Implement the milestone:

Complete V1 visual polish and interaction refinement.

The V1 design system, shared application shell, guided form workflows,
redesigned Event Analysis workspace, and redesigned management screens now
exist.

Perform the final whole-application visual and interaction refinement pass.

This milestone should make the product feel cohesive, deliberate, and
production-quality across every current screen and state.

Do not redesign major workflows or screen architecture from scratch.

Do not change calculations, business rules, persistence, routes, database
behavior, backup behavior, comparison behavior, or workflow meaning.

Primary objective

Polish the existing application until it feels like one complete professional
desktop product.

The quality bar is comparable in clarity, restraint, consistency, and finish to
modern products such as:

- Notion
- ChatGPT
- Linear
- Stripe Dashboard
- Zillow

Do not imitate those products.

Use them only as references for:

- visual consistency
- typography
- spacing
- interaction quality
- restrained motion
- feedback states
- wording
- attention to edge cases

Definition of done

A user should be able to move through the entire application without
encountering a screen, control, message, spacing decision, or state that:

- looks unfinished
- feels visually inconsistent
- appears to belong to a different product
- uses unclear wording
- behaves unexpectedly
- looks like an engineering placeholder

Do not add visual novelty merely to make the diff appear substantial.

This is a consistency and friction audit.

- font weights
- line heights
- heading hierarchy
- label hierarchy
- supporting text
- numeric emphasis
- table and row text
- captions
- metadata
- dialog text

Requirements:

- section headings should be easy to scan
- body copy should be comfortable to read
- labels should be concise
- important figures should have clear emphasis
- supporting text should not compete with primary content

Motion and transitions

Use motion only to explain change.

Appropriate uses include:

- panel expansion and collapse
- dialog entry and exit
- step transitions
- selected-state changes
- saving acknowledgement
- recalculation acknowledgement
- loading completion
- success-message appearance

Use short, subtle transitions, generally around 120–200 milliseconds.

Motion should:

- feel calm
- never delay interaction
- never block input
- never distract from data
- respect reduced-motion preferences

Avoid:

- decorative entrance animation
- bouncing controls
- constant pulsing
- motion on every hover
- long fades
- large movement across the screen
- animation that obscures state changes

Loading, saving, and asynchronous behavior

Standardize asynchronous feedback.

Every asynchronous action should clearly communicate:

1. The action started.
2. The action is still working, if it takes noticeable time.
3. The action succeeded or failed.
4. Whether the customer may act again.

Cover:

- Event Analysis recalculation
- Scenario save
- Save as new Scenario
- overwrite
- reset
- Event rename
- Scenario rename
- delete actions
- backup creation
- restore validation
- restore execution
- application startup
- database recovery actions

Requirements:

- prevent accidental duplicate submissions
- preserve the current view during short operations
- do not show a spinner for work that completes instantly
- use button loading states where appropriate
- retain entered values on failure
- use concise success confirmation
- keep technical errors out of customer-facing messages
- do not allow stale asynchronous responses to overwrite newer state

Recalculation should feel immediate.

Use subtle status text or a brief visual update acknowledgement only when it
improves confidence.

Feedback system

Use one consistent feedback model.

Inline validation:

- field-level input problems
- attached directly to the relevant control
- may block progress or submission

Contextual warnings:

- business-risk information
- placed beside the causal assumption group
- nonblocking
- factual
- updated live

Success feedback:

- compact
- specific
- non-disruptive
- should not require dismissal for routine actions

Error feedback:

- clear
- recoverable where possible
- explains the next step
- never exposes raw technical details

Dialogs:

- only for required decisions, confirmations, or destructive actions
- not for routine success messages
- not when inline feedback is sufficient

Standardize feedback for:

- saved
- renamed
- deleted
- restored
- validation failed
- backup failed
- restore failed
- record missing
- unsaved changes
- recovery required
