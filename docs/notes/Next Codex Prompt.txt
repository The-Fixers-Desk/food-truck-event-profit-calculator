Implement the milestone:

Add database versioning and safe migrations.

The application currently has a working SQLite schema containing Business
Defaults, Events, Event Scenarios, employee labor rows, miscellaneous-cost
rows, and other established application data.

Add a formal migration system that supports safe future schema upgrades while
preserving all existing customer data.

Version 1 baseline

Treat the complete schema that exists at the beginning of this milestone as
the official Version 1 schema.

Inspect the current database initialization, repositories, tables, columns,
indexes, foreign keys, constraints, and scaled-integer persistence conventions
before changing the initialization process.

Do not change the meaning or structure of existing application data merely to
introduce versioning.

Migration ledger

Add a migration ledger table named:

schema_migrations

Store at least:

- version
- name
- applied_at

Rules:

- Version must be a unique sequential integer.
- Migration records are immutable after successful application.
- Record a migration only after its complete schema operation and verification
  succeed.
- The highest successfully recorded version represents the current database
  schema version.
- Define the application’s latest supported schema version explicitly.

Do not use session state or application memory as the source of schema version
truth.

Fresh database behavior

A completely new empty database must:

- Create the migration ledger.
- Apply the Version 1 migration.
- Create the complete current application schema.
- Record Version 1 only after schema creation succeeds.
- Be immediately usable by all existing application workflows.

Fresh setup and existing-database upgrades must produce the same final schema.

Existing unversioned database adoption

Existing customer databases currently have application tables but no migration
ledger.

Support adopting a compatible unversioned database as Version 1 without
rebuilding or rewriting it.

Before adoption:

- Inspect all expected Version 1 tables.
- Verify required columns and compatible types.
- Verify important indexes, foreign keys, and relationships.
- Verify the expected Defaults, Event, Scenario, labor, and miscellaneous-cost
  structures.
- Run an appropriate SQLite integrity or quick check.
- Run a foreign-key check where applicable.

When the unversioned database is compatible:

- Create the migration ledger safely.
- Record Version 1.
- Preserve every existing row and identifier.
- Do not rename, recreate, copy, or reorder existing business data merely to
  stamp the version.

When the database is incomplete, conflicting, or not recognizably compatible:

- Do not stamp it as Version 1.
- Do not attempt destructive repairs.
- Stop startup safely.
- Log the technical reason.
- Show the customer the application’s normal friendly database-startup error.

Do not silently reinterpret an unknown schema.

Already-versioned database behavior

When the database is already at the latest supported version:

- Perform no migration writes.
- Do not update migration timestamps.
- Do not rerun migration functions.
- Continue normal application startup.

When the database is behind the latest supported version:

- Apply every missing migration in numerical order.
- Do not skip versions.
- Stop immediately if any migration fails.

When the database version is newer than the application supports:

- Refuse to open it for normal operation.
- Do not downgrade it.
- Do not modify its schema or version records.
- Provide a clear error indicating that a newer application version is
  required.

Migration execution

Create a clear migration registry or equivalent ordered structure containing:

- Version number
- Migration name
- Migration function

Migration execution must occur:

- After the database path and connection behavior are established
- Before repositories, routes, or normal application workflows use the schema

Each migration must:

- Use the project’s existing transaction behavior.
- Be atomic.
- Validate its expected starting state.
- Apply only its intended changes.
- Validate its resulting state.
- Record its version last.

If any schema operation, data-copy operation, verification step, or ledger
write fails:

- Roll back the complete migration.
- Leave the database at its previous successfully recorded version.
- Do not continue to later migrations.
- Do not allow normal application startup.

Do not broadly catch and ignore SQLite schema errors.

Temporary-table safety

For migrations that eventually need table reconstruction:

- Use a unique migration-specific temporary table name.
- Do not use generic names such as prior_defaults.
- Verify that the intended temporary name does not unexpectedly exist.
- Treat an unexpected leftover table as a migration conflict rather than
  silently reusing or deleting it.
- Copy data explicitly.
- Verify copied row counts and required relationships before replacing the
  original table.
- Drop old or temporary structures only after successful verification.

Document this required pattern even if Version 1 itself does not need table
reconstruction.

Schema initialization

Replace or adapt the existing parallel schema-initialization behavior so schema
creation and upgrading are governed by the migration system.

Do not leave a separate initialization path that can silently create missing
columns or tables and make a damaged database appear valid.

Existing initialization helpers may be reused by the Version 1 migration when
that remains clear and safe.

All current tests and normal application behavior must continue to work.

Logging and errors

Log:

- The database version detected at startup
- Every migration beginning
- Every migration successfully completed
- Adoption of a compatible unversioned database
- Migration or compatibility failures

Do not log sensitive customer data.

Use the existing customer-facing error-handling system rather than exposing raw
SQLite tracebacks in the interface.

Data preservation

Explicitly preserve:

- Business Defaults
- Labor defaults
- Events
- Event identity
- Event Scenarios
- Scenario assumptions
- Scenario names
- Ordered employee labor entries
- Ordered miscellaneous-cost entries
- All identifiers and relationships
- Created and modified timestamps

Do not delete, reset, or manually replace data/app.db.

Tests must never use or modify the real customer database.

- Migration Version 1 being recorded exactly once
- Restarting an already-current database performing no migration writes
- A compatible unversioned database being adopted as Version 1

Create test fixtures or temporary database copies representing:

Implement the milestone:

Add backup, restore, and recovery safeguards.

Database versioning and safe migrations, transactional repositories, and the
complete customer-data schema already exist.

Build customer-facing backup and restore behavior, automatic recovery

Backup format

Create a versioned portable backup format using the file extension:

.ftbackup

The backup should be a ZIP-compatible archive created with Python’s standard
library and contain:

- A consistent SQLite database snapshot
- A JSON manifest

The manifest must contain at least:

- Backup-format version
- Application version
- Database schema version
- Backup creation timestamp
- Database filename
- SHA-256 checksum of the database snapshot

Use SQLite’s supported connection backup API to create the snapshot.

Do not copy the active database file directly.

Before producing a customer backup:

- Complete or safely coordinate active database work.
- Create the database snapshot in a temporary location beneath the configured
  application-data directory.
- Run an SQLite integrity check on the completed snapshot.
- Run a foreign-key check.
- Calculate and record its checksum.
- Package the snapshot and manifest.
- Remove temporary working files after success or failure.

Do not include:

- Logs
- Caches
- Temporary uploads
- Previous backups
- Application code or installed files

Customer-facing backup workflow

Add a functional Data Safety screen accessible from the established
application navigation or Dashboard.

Provide a clear action labeled:

“Download backup”

When selected:

- Create a fresh backup.
- Return it as a downloadable .ftbackup file.
- Use a useful timestamped filename.
- Do not expose server or local filesystem paths.
- Do not modify customer data.

If backup creation fails:

- Do not return a partial archive.
- Remove incomplete temporary files.
- Preserve the live database.
- Show the existing friendly customer-facing error behavior.
- Log the technical cause without logging customer content.

Restore workflow

Provide a customer-facing action labeled:

“Restore backup”

Allow the customer to select a .ftbackup file through the existing local web
interface.

Restore is a complete replacement operation. It does not merge records.

Clearly explain that restoring will replace the current:

- Business Defaults
- Events
- Scenarios
- Labor entries
- Miscellaneous-cost entries
- Other saved application data

Require explicit confirmation before replacing the current database.

Backup validation

Before modifying the live database:

- Save the uploaded archive to a controlled temporary location beneath the
  application-data directory.
- Reject unexpectedly large, malformed, unsafe, or path-traversing archives.
- Read and validate the manifest.
- Verify the supported backup-format version.
- Verify required manifest values.
- Extract only the expected database file.
- Verify the SHA-256 checksum.
- Verify that the extracted file is a recognizable SQLite database.
- Run an SQLite integrity check.
- Run a foreign-key check.
- Inspect its migration ledger and schema version.
- Verify that its schema is recognizable and supported.

Do not trust filenames or paths contained in the archive.

Schema compatibility

When the restored database is at the current supported schema version:

- Restore it without unnecessary schema writes.

When it is from an older supported schema version:

- Restore it to a staging location.
- Run the existing migration system against the staged database.
- Validate the fully migrated database before replacing the live database.

When its schema version is newer than the application supports:

- Reject the restore.
- Explain that the backup requires a newer application version.
- Do not modify current customer data.

When the database is damaged, incomplete, foreign-key-invalid, or incompatible:

- Reject the restore safely.
- Preserve current customer data.
- Show a useful customer-facing message.

Pre-restore recovery snapshot

Immediately before replacing the current database:

- Create an automatic recovery snapshot of the current live database using the
  same safe SQLite backup mechanism.
- Store it in an automatic-recovery directory beneath the application-data
  directory.
- Include a manifest or metadata identifying it as a pre-restore snapshot.
- If the recovery snapshot cannot be created and validated, abort the restore.

Restore replacement

Never overwrite the active database incrementally.

Use this general sequence:

1. Validate and, if necessary, migrate the uploaded database in staging.
2. Validate the staged final database.
3. Create and validate a pre-restore recovery snapshot.
4. Close or coordinate all active live-database connections.
5. Replace the live database using a safe atomic filesystem operation where
   supported.
6. Reopen the database.
7. Verify schema version, integrity, and foreign keys.
8. Confirm normal repository access before reporting success.

If replacement or post-replacement verification fails:

- Do not leave a partially written database.
- Attempt to restore the validated pre-restore recovery snapshot.
- Preserve failed files for technical diagnosis when safe.
- Stop normal operation rather than continuing with uncertain data.
- Log the recovery sequence without exposing customer content.

After a successful restore:

- Clear stale session references to Events, Scenarios, workspaces, and
  temporary navigation state.
- Re-evaluate setup completion from restored Business Defaults.
- Open the appropriate Welcome or Dashboard route.
- Display a clear success message.

Automatic migration recovery snapshots

Integrate with the existing migration startup process.

Before applying one or more missing production migrations to a customer
database:

- Create and validate an automatic pre-migration recovery snapshot.
- Abort migration if that snapshot cannot be safely created.
- Do not create another snapshot when the database is already current and no
  migration will run.

A failed migration must continue using the migration system’s existing
transaction and rollback rules.

Do not silently restore a pre-migration snapshot unless needed to recover from
a database state that cannot be returned to its prior version transactionally.

Automatic recovery retention

Keep the five most recent validated automatic recovery snapshots.

After successfully creating a new automatic snapshot:

- Remove only older snapshots beyond the retention limit.
- Never delete the newly created snapshot.
- Ignore unrelated files.
- Do not let cleanup failure invalidate an otherwise valid snapshot or
  operation; log the cleanup failure instead.

Customer-created downloaded backups are not managed by this retention rule.

Damaged-database startup behavior

At startup, continue using the migration system’s compatibility checks.

When the live database fails integrity, foreign-key, schema, or migration
validation:

- Do not modify or delete the damaged database automatically.
- Do not silently replace it with a recovery snapshot.
- Preserve the damaged database.
- Prevent normal routes and repositories from using it.
- Show a friendly recovery state explaining that customer data could not be
  opened and that a valid backup may be restored.

When practical, make the Restore backup workflow available from this recovery
state without exposing unrelated application functions.
