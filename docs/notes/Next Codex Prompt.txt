Implement the milestone:

Add automatic initial scenario saving and workspace version actions.

The interactive Event Analysis workspace, calculation engine, break-even
analysis, warnings, Event and Event Scenario schema, and complete validation
already exist.

Change the workflow so every valid Event Inputs submission is saved before the
Event Analysis workspace opens.

Initial Event Inputs submission

When the customer submits a complete, valid Event Inputs form:

- Create an Event containing the submitted event identity:
  - Event name
  - Event date
  - Start time
  - Location

- Create the Event’s first Scenario automatically.
- Name the first Scenario:
  “Original estimate”
- Save the complete submitted assumptions and ordered child entries.
- Create the Event and first Scenario in one database transaction.
- If any part of the save fails, create neither record.
- Do not open the workspace unless persistence succeeds.
- After a successful save, open the Event Analysis workspace with the newly
  created Scenario as the active Scenario and reset baseline.

Invalid Event Inputs submissions must:

- Remain on the Event Inputs form
- Display the existing validation errors
- Preserve every submitted value and repeatable row
- Create no Event or Scenario records

Duplicate Event submissions

Do not attempt to detect or merge Events based on matching names, dates, times,
or locations.

Each valid submission from the new Event Inputs workflow creates a new Event
and its own “Original estimate” Scenario.

Scenario persistence

An Event stores shared event identity.

An Event Scenario stores one complete set of adjustable analysis assumptions,
including:

- Attendance and weather assumptions
- Percentage expected to buy food
- Other competing food vendors
- Revenue method and custom expected-sales state
- Average order amount
- Food and packaging method and matching value
- Card-payment assumptions
- Ordered employee labor entries
- Owner labor pay
- Travel and operating costs
- Event and payment fees
- Ordered named miscellaneous costs
- Profit-target type and matching value

Persist assumptions, not calculated financial results.

Whenever a Scenario opens, regenerate its results through the existing Python
calculation engine.

Workspace behavior

The workspace always represents an active saved Scenario.

Allow the customer to change assumptions freely without automatically modifying
the active saved Scenario.

Track whether the current workspace assumptions differ from the active saved
baseline.

- Changes make the workspace dirty.
- Returning every value and ordered row to the baseline clears the dirty state.
- Reset changes restores the active Scenario’s saved assumptions and
  recalculates the analysis.

Save action

Add one primary workspace button labeled:

“Save”

Disable it when the workspace has no unsaved changes.

When clicked, open an accessible save dialog or equivalent inline flow with
these choices:

1. Save as new scenario
2. Overwrite current scenario

“Save as new scenario” must be selected by default every time the save flow
opens.

Save as new scenario

When this option is selected:

- Require the customer to enter a nonblank Scenario name.
- Trim surrounding whitespace before saving.
- Create a new Scenario under the same Event.
- Copy the complete current workspace assumptions and ordered child entries
  into the new Scenario.
- Do not modify the previously active Scenario.
- After success:
  - Make the new Scenario the active Scenario
  - Show its name in the workspace
  - Treat its saved values as the new reset baseline
  - Clear the dirty state
  - Display a clear success state

Scenario names must be unique within the same Event after trimming whitespace
and without regard to capitalization.

The same Scenario name may be used under a different Event.

On a duplicate name:

- Do not save
- Preserve the entered name
- Preserve all workspace assumptions and results
- Show a clear validation message
- Do not silently alter the name

Overwrite current scenario

When this option is selected:

- Clearly identify the Scenario that will be replaced.
- Require an explicit confirmation before writing.
- Update only the active Scenario.
- Preserve its Scenario identity and name.
- Do not modify sibling Scenarios.
- Do not modify the Event identity.
- Do not modify Business Defaults.
- Replace its stored assumptions and ordered child rows transactionally.
- Update its modified timestamp.

After success:

- Keep the same Scenario active
- Treat the overwritten state as the new reset baseline
- Clear the dirty state
- Display a clear success state

Do not use “Save changes” as a separate primary action. The single Save flow
must default to creating a new Scenario while still allowing deliberate
overwriting.

Validation and failures

- Never save an invalid workspace state.
- Reuse the existing complete form and domain validation.
- Preserve all entered values and repeatable rows after a failed save.
- Keep displaying the most recent valid calculation results.
- Show customer-facing save errors without navigating away.
- Use database transactions for every Scenario write.
- A failed child-row write must not partially create or modify a Scenario.
- Business Defaults must remain unchanged.

Data integrity

- Persist scaled integer values using the project’s established conventions.
- Preserve employee labor and miscellaneous-cost row order.
- Maintain Event-to-Scenario foreign-key relationships.
- Reuse existing repositories and persistence patterns where practical.
- Do not delete, reset, or manually replace data/app.db.
- Preserve unrelated application and customer data.

Scope

Do not implement yet:

- Saved-event or saved-scenario lists
- Opening a Scenario from a saved-work screen
- Scenario renaming after creation
- Scenario deletion
- Event deletion
- Event identity editing
- Scenario comparison
- Dashboard behavior
- Final visual polish

Do not add dependencies.
Do not make unrelated changes.
Do not commit.

- Separate submissions creating separate Events
