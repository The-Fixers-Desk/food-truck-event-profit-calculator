Migration ledger

Add a migration ledger table named:

schema_migrations

Store at least:

- version
- name
- applied_at

Rules:

- Version must be a unique sequential integer.
- Migration records are immutable after successful application.
- Record a migration only after its complete schema operation and verification

Fresh database behavior

A completely new empty database must:

- Create the migration ledger.
- Apply the Version 1 migration.
- Create the complete current application schema.
- Record Version 1 only after schema creation succeeds.
- Be immediately usable by all existing application workflows.

Fresh setup and existing-database upgrades must produce the same final schema.

Existing unversioned database adoption

Existing customer databases currently have application tables but no migration
ledger.

Already-versioned database behavior

- Perform no migration writes.
- Do not update migration timestamps.

- Refuse to open it for normal operation.
- Do not downgrade it.
- Do not modify its schema or version records.

- Migration name
- Migration function

- Use the project’s existing transaction behavior.

- Validate its expected starting state.
- Apply only its intended changes.
- Validate its resulting state.

Backup format

Create a versioned portable backup format using the file extension:

.ftbackup

The backup should be a ZIP-compatible archive created with Python’s standard
library and contain:

- A consistent SQLite database snapshot
- A JSON manifest

The manifest must contain at least:

- Backup-format version
- Application version
- Database schema version
- Backup creation timestamp
- Database filename
- SHA-256 checksum of the database snapshot

Use SQLite’s supported connection backup API to create the snapshot.

Do not copy the active database file directly.

Before producing a customer backup:

- Complete or safely coordinate active database work.
- Create the database snapshot in a temporary location beneath the configured
  application-data directory.
- Run an SQLite integrity check on the completed snapshot.
- Run a foreign-key check.
- Calculate and record its checksum.
- Package the snapshot and manifest.
- Remove temporary working files after success or failure.

Do not include:

- Logs
- Caches
- Temporary uploads
- Previous backups
- Application code or installed files

Add a functional Data Safety screen accessible from the established

Restore workflow

“Restore backup”

Backup validation

Before modifying the live database:

- Save the uploaded archive to a controlled temporary location beneath the
  application-data directory.
- Reject unexpectedly large, malformed, unsafe, or path-traversing archives.
- Read and validate the manifest.
- Verify the supported backup-format version.
- Verify required manifest values.
- Extract only the expected database file.
- Verify the SHA-256 checksum.
- Verify that the extracted file is a recognizable SQLite database.
- Run an SQLite integrity check.
- Run a foreign-key check.
- Inspect its migration ledger and schema version.
- Verify that its schema is recognizable and supported.

Do not trust filenames or paths contained in the archive.

Schema compatibility

When the restored database is at the current supported schema version:

- Restore it without unnecessary schema writes.

When it is from an older supported schema version:

- Restore it to a staging location.
- Run the existing migration system against the staged database.
- Validate the fully migrated database before replacing the live database.

When its schema version is newer than the application supports:

- Reject the restore.
- Explain that the backup requires a newer application version.
- Do not modify current customer data.

When the database is damaged, incomplete, foreign-key-invalid, or incompatible:

- Reject the restore safely.
- Preserve current customer data.
- Show a useful customer-facing message.

Pre-restore recovery snapshot

Immediately before replacing the current database:

- Create an automatic recovery snapshot of the current live database using the
  same safe SQLite backup mechanism.
- Store it in an automatic-recovery directory beneath the application-data
  directory.
- Include a manifest or metadata identifying it as a pre-restore snapshot.
- If the recovery snapshot cannot be created and validated, abort the restore.

Restore replacement

Never overwrite the active database incrementally.

Use this general sequence:

1. Validate and, if necessary, migrate the uploaded database in staging.
2. Validate the staged final database.
3. Create and validate a pre-restore recovery snapshot.
4. Close or coordinate all active live-database connections.
5. Replace the live database using a safe atomic filesystem operation where
   supported.
6. Reopen the database.
7. Verify schema version, integrity, and foreign keys.
8. Confirm normal repository access before reporting success.

If replacement or post-replacement verification fails:

- Do not leave a partially written database.
- Attempt to restore the validated pre-restore recovery snapshot.
- Preserve failed files for technical diagnosis when safe.
- Stop normal operation rather than continuing with uncertain data.
- Log the recovery sequence without exposing customer content.

After a successful restore:

- Clear stale session references to Events, Scenarios, workspaces, and
  temporary navigation state.
- Re-evaluate setup completion from restored Business Defaults.
- Open the appropriate Welcome or Dashboard route.
- Display a clear success message.

Automatic migration recovery snapshots

Integrate with the existing migration startup process.

Before applying one or more missing production migrations to a customer
database:

- Create and validate an automatic pre-migration recovery snapshot.
- Abort migration if that snapshot cannot be safely created.
- Do not create another snapshot when the database is already current and no
  migration will run.

A failed migration must continue using the migration system’s existing
transaction and rollback rules.

Do not silently restore a pre-migration snapshot unless needed to recover from
a database state that cannot be returned to its prior version transactionally.

Automatic recovery retention

Keep the five most recent validated automatic recovery snapshots.

After successfully creating a new automatic snapshot:

- Remove only older snapshots beyond the retention limit.
- Never delete the newly created snapshot.
- Ignore unrelated files.
- Do not let cleanup failure invalidate an otherwise valid snapshot or

Customer-created downloaded backups are not managed by this retention rule.
