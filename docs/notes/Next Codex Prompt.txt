Local server

Start the existing Flask application through a controllable Werkzeug server,
such as an appropriate make_server-based implementation.

Requirements:

- Do not bind to 0.0.0.0 or expose the application to the local network.
- Allow the operating system to assign an available port.
- Do not assume a fixed port is free.
- Run the server in a managed background thread.
- Disable the Flask debug server and reloader.
- Make server startup failure observable to the shell.
- Provide or reuse a lightweight local readiness check.
- Do not expose sensitive application or database information through the
  readiness response.

Single-instance protection

Implement a cross-platform single-instance guard using an operating-system
file lock or equivalent standard-library behavior.

Support:

- Windows locking behavior
- macOS locking behavior
- Development environments used by the test suite

The lock file must live beneath the centralized application-data directory.

When another application instance already holds the lock:

- Do not start another server.
- Do not open another application window.
- Show a brief customer-facing message stating that the application is already
  open.
- Exit normally.
- Do not delete or override the active instance’s lock.

A stale file without an active operating-system lock must not permanently
prevent startup.

Release the lock after normal shutdown and after handled startup failure.

Do not implement foreground activation of the existing window in this
milestone.

Startup sequence

Defect workflow

Create a concise acceptance-defect log.

For every confirmed defect, record:

- Defect identifier
- Environment
- Artifact checksum
- Reproduction steps
- Expected behavior
- Actual behavior
- Severity
- Release-blocking decision and rationale

- Files changed

- Focused test result
- Full-suite result
- Rebuilt artifact checksum
- Acceptance retest result

Before fixing:

- Reproduce the problem reliably.
- Confirm it occurs in the tested release candidate.
- Distinguish product defects from test-environment failures.

For every release-blocking defect:

1. Add or update an automated regression test where technically practical.
2. Fix the smallest underlying cause.
3. Do not work around data-integrity or calculation problems only in the UI.
4. Run focused tests.
5. Run the full automated suite.
6. Run git diff --check.
7. Rebuild the affected packaged artifact.
8. Repeat the failed acceptance test.
9. Repeat adjacent critical workflows that could have regressed.
10. Update the acceptance record and defect log.

If a blocker cannot be fixed safely within this milestone:

- Leave it open and clearly documented.
- Do not mark the platform release-ready.
- Do not conceal it with wording changes or skipped tests.
