Implement the milestone:

Redesign dashboards and saved-work views.

The V1 design system, shared application shell, guided form workflows, and
redesigned Event Analysis workspace now exist.

Redesign the Dashboard, Welcome, Saved Events, Scenario Comparison, Data Safety,
and related management screens into one cohesive, efficient system.

Apply the established V1 design system, application shell, reusable page
layouts, form components, workspace components, and action hierarchy.

Do not change calculations, persistence, routes, database behavior, backup
semantics, comparison rules, or workflow meaning.

Primary objective

These screens should feel like a unified professional desktop application, not
a collection of disconnected management pages.

The quality bar is comparable in clarity, restraint, scanability, and workflow
efficiency to products such as:

- Notion
- ChatGPT
- Linear
- Stripe Dashboard
- Zillow

Do not imitate those products.

Use them only as references for:

- information architecture
- management-screen density
- restrained use of cards
- clear empty states
- searchable libraries
- aligned comparisons
- professional onboarding
- action hierarchy

Shared management patterns

Create or refine reusable patterns for:

- search

- status badges

- row actions
- overflow actions

Dashboard

Redesign the Dashboard as a decision and launch screen.

It should answer:

- What should I do next?
- What have I worked on recently?
- Is anything asking for attention?

Primary action:

Analyze new event

Recommended structure:

1. Compact welcome or page context
2. Primary Analyze new event action
3. Continue where you left off
4. Recent Events or Scenarios
5. Useful shortcuts to:
   - Saved Events
   - Business Defaults
   - Data Safety

Use only genuinely useful summaries.

Do not add:

- fake analytics
- vanity metrics
- invented trends
- decorative charts
- business statistics not already supported by application data

If the app has no recent work, show a concise empty state with one obvious
action.

The Dashboard should fit within one ordinary desktop viewport where practical.

Welcome and first-use orientation

Redesign Welcome as brief orientation into a professional tool.

The screen should:

- explain the product within seconds
- present the established four-step introduction
- make Get started immediately obvious
- show what the customer will accomplish
- preserve setup detection and current onboarding flow

Avoid:

- long paragraphs
- large marketing-style sections
- decorative landing-page content
- testimonials
- invented product claims
- excessive scrolling

Primary action:

Get started

The four steps should feel compact, sequential, and operational.

Do not change the number, meaning, or routing of onboarding steps.

Saved Events

Redesign Saved Events as a compact work library.

It should optimize for:

- finding work
- understanding Event and Scenario identity
- reopening analysis quickly
- managing saved records safely

Primary action for each record:

Open analysis

Add or refine lightweight controls for:

- search by Event or Scenario name
- sort by modified date
- sort by Event date
- sort by name

Use only existing record data.

Do not add new persistence merely to support search or sorting.

Preferred layout:

- compact Event rows or grouped sections
- Event name
- Event date
- location where useful
- Scenario count
- latest activity or modified date
- clear primary open action
- secondary rename and delete actions
- progressive disclosure for Scenario lists where useful

Do not make every Event a large card.

Do not hide all Scenario information behind multiple unnecessary clicks.

Scenario rows should clearly show:

- Scenario name
- associated Event
- relevant status or outcome where already available
- modified date where available
- Open analysis action
- secondary rename or delete actions

Preserve:

- Event deletion confirmation
- rename validation
- duplicate-name rules
- missing-record handling
- persistence after restart

Empty state:

- title explaining that no Events are saved
- one concise sentence
- primary Analyze new event action

Data Safety

Redesign Data Safety to create confidence without unnecessary alarm.

Use two clear primary task areas:

1. Download backup
2. Restore backup

Primary normal action:

Download backup

Restore should remain clearly available but visually distinct because it is a
higher-impact action.

Explain concisely:

- what the backup includes
- that restore replaces current application data
- that restore is not a merge
- when a recovery snapshot is created
- that backups remain local

Put longer or technical explanations behind progressive disclosure.

Do not expose:

- internal paths
- database implementation details
- raw archive structure
- stack traces
- SQL terminology

Preserve all existing:

- backup validation
- checksum validation
- unsupported-version rejection
- restore confirmation
- pre-restore recovery snapshot
- replacement behavior
- failure safeguards
- recovery behavior

The screen should not look like an emergency state during normal use.

Recovery screens may remain more caution-oriented where appropriate.
