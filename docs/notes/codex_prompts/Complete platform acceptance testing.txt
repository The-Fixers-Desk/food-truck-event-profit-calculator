Implement the milestone:

Complete platform acceptance testing and fix V1 defects.

The Windows and macOS packages, desktop shell, complete automated end-to-end
suite, calculations, persistence, backup and restore, accessibility, and all V1
customer workflows already exist.

Perform release-candidate acceptance testing against the actual packaged
Windows and macOS applications. Resolve every confirmed release-blocking defect
that can be reproduced, then rebuild and retest the affected artifacts.

Do not treat source-mode Flask execution as platform acceptance testing.

Acceptance-test records

Create a structured V1 acceptance-test record in the repository.

For every performed check, record:

- Test identifier
- Platform
- Architecture
- Operating-system version
- Application version
- Artifact filename
- Artifact SHA-256 checksum
- Clean, upgrade, reinstall, or recovery environment
- Preconditions
- Steps performed
- Expected result
- Actual result
- Pass, fail, blocked, or not run
- Evidence or concise notes
- Related defect identifier when applicable
- Retest result after a fix

Clearly distinguish:

- Passed
- Failed
- Blocked by an unavailable environment or credential
- Not run

Never mark an unavailable check as passed.

Release-blocking definition

Treat a confirmed defect as release-blocking when it causes or creates a
material risk of:

- Failure to install
- Failure to launch
- Failure to close cleanly
- Local server or process remaining active after application closure
- Data loss
- Data corruption
- Partial database writes
- Unsafe schema migration
- Customer data being written into installed application resources
- Customer data being deleted during upgrade, reinstall, replacement, or
  uninstall
- Backup creation failure in an otherwise supported state
- Valid backup restoration failure
- Invalid backup being accepted
- Recovery safeguards failing
- Incorrect financial calculations
- Incorrect profit, margin, break-even, demand, or warning results
- Saved assumptions loading incorrectly
- A core V1 workflow being unusable
- Scenario version actions overwriting the wrong Scenario
- Comparison displaying results from the wrong assumptions
- Setup or route safeguards allowing an unusable application state
- Single-instance protection allowing conflicting writes
- Required offline workflows depending on external network access
- A serious keyboard or screen-reader barrier that prevents completion of a
  core workflow
- Windows prerequisite handling preventing supported installation
- macOS signing, notarization, Gatekeeper, architecture, or bundle defects that
  prevent the intended supported distribution

Do not classify as release-blocking solely because of:

- Minor spacing inconsistencies
- Small wording preferences
- Nonessential animation or transition behavior
- Cosmetic differences between platforms
- Development-only unsigned-build warnings that are already documented and do
  not affect the intended signed release process

Document nonblocking defects separately without expanding this milestone into
new product work.

Windows test matrix

Where clean environments are available, test:

- Windows 10 x64
- Windows 11 x64

For each tested Windows version, cover the following.

Clean installation:

- Installer launches without requiring administrator elevation.
- WebView2 detection works when the Runtime is already installed.
- Bundled offline WebView2 installation works when the Runtime is absent.
- A WebView2 prerequisite failure stops installation safely.
- Application files install under the configured per-user program location.
- Customer data is created under the configured LocalAppData location.
- No mutable customer data is written beside the executable.
- Start Menu shortcut works.
- Desktop shortcut behavior matches the installer choice.
- Add/Remove Programs metadata is correct.
- Application launches without a console window.
- Product title, version, and icon are correct.
- First-use onboarding works.

Core customer workflow:

- Save Business Defaults.
- Create a complete Event.
- Verify automatic Original estimate creation.
- Use live Event Analysis recalculation.
- Save as a new Scenario.
- Overwrite the active Scenario deliberately.
- Open saved work.
- Rename and delete permitted records.
- Compare Scenarios.
- Download a backup.
- Restore a valid backup.
- Reject an invalid backup.
- Verify restored data after restart.

Desktop behavior:

- Second launch is rejected safely.
- Closing the window stops the local server.
- Closing releases the instance lock.
- Application can start again afterward.
- Window resizing preserves usable layouts.
- Keyboard navigation remains usable.
- No ordinary workflow opens a browser window unexpectedly.

Existing data and upgrade:

- Install over an older supported package.
- Preserve Defaults, Events, Scenarios, backups, and recovery snapshots.
- Run pending database migrations safely.
- Produce only one installed-program entry.
- Preserve working shortcuts.
- Open the correct Dashboard or Welcome state afterward.

Same-version reinstall:

- Reinstall successfully.
- Preserve all customer data.
- Avoid duplicate shortcuts and installed-program entries.

Uninstall and reinstall:

- Remove installer-owned application files and shortcuts.
- Preserve LocalAppData customer records.
- Reinstall successfully.
- Reconnect to preserved customer data.

Offline operation:

- Install without internet access.
- Launch without internet access.
- Complete representative core workflows without internet access.
- Use only the local loopback server.

Failure and recovery:

- Damaged database enters the established recovery state.
- Damaged data is not silently deleted or replaced.
- Restore remains available where designed.
- Interrupted or failed startup preserves customer data.
- Installer failure does not remove established customer data.
- Running-application installation and uninstall handling is safe.

macOS release verification

When valid Developer ID and notarization credentials are available:

- Sign nested executable code correctly.
- Sign the outer application bundle last.
- Verify Hardened Runtime.
- Verify bundle identifier and version.
- Verify arm64 and x86_64 slices.
- Create and sign the DMG.
- Submit using notarytool.
- Verify successful notarization.
- Staple the ticket.
- Verify the stapled ticket.
- Verify Gatekeeper acceptance.

- Record the checks as blocked or not run.
- Do not claim the artifact is release-ready for macOS distribution.
- Do not claim signing or notarization success.
- Preserve development-build results separately.

Defect workflow

Create a concise acceptance-defect log.

For every confirmed defect, record:

- Defect identifier
- Environment
- Artifact checksum
- Reproduction steps
- Expected behavior
- Actual behavior
- Severity
- Release-blocking decision and rationale
- Root cause when identified
- Files changed
- Automated regression coverage added
- Focused test result
- Full-suite result
- Rebuilt artifact checksum
- Acceptance retest result

Before fixing:

- Reproduce the problem reliably.
- Confirm it occurs in the tested release candidate.
- Distinguish product defects from test-environment failures.

For every release-blocking defect:

1. Add or update an automated regression test where technically practical.
2. Fix the smallest underlying cause.
3. Do not work around data-integrity or calculation problems only in the UI.
4. Run focused tests.
5. Run the full automated suite.
6. Run git diff --check.
7. Rebuild the affected packaged artifact.
8. Repeat the failed acceptance test.
9. Repeat adjacent critical workflows that could have regressed.
10. Update the acceptance record and defect log.

If a blocker cannot be fixed safely within this milestone:

- Leave it open and clearly documented.
- Do not mark the platform release-ready.
- Do not conceal it with wording changes or skipped tests.

Automated regression testing

After acceptance fixes:

- Run all focused tests related to changed behavior.
- Run the complete unit, integration, route, migration, backup, shell,
  packaging, accessibility, and end-to-end test suite.
- Run the Chromium full E2E suite.
- Run the Firefox and WebKit smoke suites where browser binaries are available.
- Run desktop lifecycle tests.
- Run offline tests.
- Run packaging audits.
- Run git diff --check.

Do not weaken existing tests to make acceptance fixes pass.
