Implement the milestone:

Package the Windows application.

The desktop application shell, centralized data-directory system, database
migrations, backup and restore safeguards, offline interface, and complete
customer workflows already exist.

Create a reproducible 64-bit Windows application bundle and installer.

Packaging target

Support:

- Windows 10 x64
- Windows 11 x64

Do not build:

- 32-bit Windows packages
- ARM64 packages
- Microsoft Store or MSIX packages
- macOS packages

Use a 64-bit Windows Python environment for the production build.

Application identity

Use:

Product name:
Food Truck Event Profit Calculator

Publisher:
The Fixer’s Desk

Executable name:
FoodTruckEventProfitCalculator.exe

Installer filename pattern:
FoodTruckEventProfitCalculator-Setup-{version}-x64.exe

Define the application version in one centralized source of truth.

The desktop shell, executable metadata, installer metadata, application
display, and generated filenames must use that same version.

If the project already has an established version source, reuse it rather than
creating a conflicting system.

Use a permanent, checked-in Inno Setup AppId that remains unchanged across
future releases and upgrades.

Do not generate a different AppId for every build.

Application icon

Use one checked-in Windows .ico asset consistently for:

- Packaged executable
- Desktop window where supported
- Installer
- Start Menu shortcut
- Desktop shortcut
- Add/Remove Programs entry

Prefer an existing approved product icon when one exists.

If no final icon exists, add and use a clearly documented temporary local icon
suitable for development packaging. Do not download an icon or use copyrighted
third-party artwork.

Keep replacement of the temporary icon straightforward before V1 release.

PyInstaller bundle

Use PyInstaller to create a windowed one-folder bundle.

Create and check in a clear PyInstaller spec file.

Requirements:

- Use onedir rather than onefile.
- Suppress the console window in the customer build.
- Use the existing production desktop entrypoint.
- Bundle all required Python packages.
- Bundle Flask templates.
- Bundle static CSS and JavaScript.
- Bundle local loading and startup-error assets.
- Bundle documentation required at runtime.
- Bundle the Windows application icon.
- Include pywebview’s required Windows components.
- Exclude unrelated GUI frameworks and development packages.
- Do not bundle tests, development databases, source-control files, caches,
  local virtual environments, or customer data.
- Do not include the repository’s data/app.db.
- Do not include backups, recovery snapshots, logs, or local test artifacts.
- Ensure no absolute development-machine paths remain in the package.

Resolve bundled read-only resources correctly in both:

- Normal source execution
- PyInstaller frozen execution

Use PyInstaller’s supported frozen-runtime behavior rather than relying on the
current working directory.

The packaged application must launch by double-clicking the executable without
requiring:

- Python
- pip
- A virtual environment
- VS Code
- A terminal
- Internet access

Windows customer-data location

Configure packaged Windows execution to use:

%LOCALAPPDATA%\The Fixer's Desk\Food Truck Event Profit Calculator

Resolve all mutable files beneath that directory through the existing
centralized application-data path system.

Include:

- Live SQLite database
- Logs
- Automatic recovery snapshots
- Backup and restore staging
- Pywebview storage or browser-profile data
- Single-instance lock
- Shell temporary files

Requirements:

- Create required directories on first launch.
- Do not place mutable files in the installer directory.
- Do not write beside the executable.
- Do not write beneath templates, static files, or bundled resources.
- Preserve the existing configurable development-data path outside packaged
  Windows execution.
- Preserve the ability of automated tests to use isolated temporary roots.

Do not move or delete the development data/app.db during packaging or testing.

WebView2 Runtime

Use pywebview’s Windows Edge Chromium renderer.

The Windows installer must operate without internet access.

Bundle the official x64 Microsoft Edge WebView2 Evergreen Standalone Installer
as an installer prerequisite.

During installation:

- Detect whether a valid WebView2 Runtime is already installed.
- Check supported per-machine and per-user installation locations or use an
  appropriate supported detection method.
- Do not reinstall the Runtime when a valid installation exists.
- When missing, run the bundled x64 Evergreen Standalone Installer silently.
- Verify the prerequisite installation succeeded before completing the
  application installation.
- Show a clear installer error if the Runtime cannot be installed.
- Do not launch the application when the prerequisite failed.

Do not:

- Download WebView2 during installation
- Depend on an internet bootstrapper
- Bundle a Fixed Version WebView2 directory into the application
- Fall back to the deprecated MSHTML renderer

Keep the Microsoft prerequisite installer outside the installed application
directory after setup completes unless it is genuinely needed there.

Do not commit a downloaded Microsoft installer binary if repository policy
excludes third-party binaries. In that case:

- Provide a documented expected local build path.
- Add an acquisition/checksum-verification build step.
- Fail the installer build clearly when the prerequisite file is absent.
- Never silently download an unverified executable.

- Per-user installation
- Normal Windows uninstall registration
- Modern compression

- Uninstaller icon where supported

Default installation directory:

%LOCALAPPDATA%\Programs\The Fixer's Desk\Food Truck Event Profit Calculator

Use the appropriate Inno Setup constants rather than hardcoding the current
Windows username or profile path.

Install the complete PyInstaller one-folder output beneath the application
installation directory.

Installation behavior

Support:

- Clean first installation
- Installation over an existing older package
- Repair-style reinstall of the same version where practical
- Launch after successful interactive installation
- Silent installation without forced application launch

When installing over an existing version:

- Reuse the stable application identity and installation location.
- Replace installed application files safely.
- Preserve customer data.
- Preserve backups and recovery snapshots.
- Preserve existing database schema and allow application startup to perform
  established migrations.
- Do not create duplicate Add/Remove Programs entries.
- Do not create duplicate shortcuts.

Do not implement automatic update discovery or downloading.

Running-application handling

Use the desktop shell’s established single-instance identity and an appropriate
installer application mutex or running-process safeguard.

When installation or uninstallation is attempted while the application is
running:

- Ask the customer to close it or close it safely through supported installer
  behavior.
- Do not terminate it during an active database write without coordination.
- Do not replace files while the running process still uses them.
- Do not corrupt or delete customer data.

Uninstallation behavior

Uninstallation should remove:

- Installed application files
- Start Menu shortcut
- Desktop shortcut created by the installer
- Installer-owned registry information
- Uninstaller files

Uninstallation must preserve:

- Customer database
- Business Defaults
- Events
- Scenarios
- Customer-created backups
- Automatic recovery snapshots
- Logs
- Other data beneath the customer-data directory

Do not offer a destructive “remove all data” checkbox in this milestone.

Where practical, show or document that customer data remains available for
reinstallation.

Reinstalling after uninstall must reconnect to the preserved data and open the
appropriate Welcome or Dashboard state.

Packaged executable verification

Test the frozen executable directly before creating the installer.

Verify:

- It launches without a console window.
- It opens one native application window.
- It starts the local server automatically.
- It uses only 127.0.0.1.
- It creates customer data in LocalAppData.
- It does not write to the bundle directory.
- It creates or opens the database correctly.
- It completes onboarding on a clean data root.
- It opens existing customer data correctly.
- Live calculations work.
- Scenario saving works.
- Backup creation works.
- Restore validation works.
- The second application launch is rejected safely.
- Closing the window stops the local server.
- It operates with external network access blocked.

Installer verification

Verify using clean, isolated Windows test environments where practical:

Clean installation:

- Installer runs without administrator elevation.
- WebView2 is detected or installed from the bundled offline prerequisite.
- Application files are installed in the correct per-user location.
- Start Menu shortcut is created.
- Desktop shortcut follows the chosen installer option.
- Add/Remove Programs entry is correct.
- Application launches successfully.
- First-use behavior works.

Existing-data installation:

- Existing LocalAppData customer records remain intact.
- Dashboard, Events, Scenarios, and Defaults load correctly.

Upgrade:

- Installing a newer package over an older package produces one installed
  product entry.
- Application files update.
- Customer data remains unchanged.
- Required database migrations run safely on launch.
- Shortcuts remain valid.

Same-version reinstall:

- Application remains launchable.
- Customer data remains intact.
- Duplicate shortcuts or uninstall entries are not created.

Uninstall:

- Application files and installer-owned shortcuts are removed.
- Customer data remains intact.
- Uninstall succeeds without internet access.
- Reinstallation finds and uses the preserved customer data.

Failure states:

- Missing WebView2 prerequisite file prevents the installer build.
- Failed WebView2 installation prevents application launch.
- A running application is handled safely.
- A damaged customer database enters the established recovery state.
- Installer failure does not remove existing customer data.
