Current behavior

A complete valid Event Inputs submission fails against an existing development
database with:

sqlite3.IntegrityError:
NOT NULL constraint failed: event_scenarios.competing_food_vendors

The same submission succeeds against a freshly created database.

Root cause

The existing Version 1 event_scenarios table contains both the legacy demand
model and the revised demand model.

Legacy required columns:

- competing_food_vendors INTEGER NOT NULL
- expected_buyer_basis_points INTEGER NOT NULL

Current revised columns:

- other_competing_food_vendors
- expected_food_buyer_basis_points

Current persistence correctly writes only the revised columns.

SQLite rejects the insert because the obsolete legacy columns remain NOT NULL
and receive no values.

The existing Version 1 schema verifier checks that required current columns are
present, but it permits these incompatible unexpected required columns and
therefore incorrectly accepts the mixed schema as compatible.

The development database currently contains:

- Events: 0
- Scenarios: 0
- Employee labor rows: 0
- Additional-cost rows: 0

Its integrity and foreign-key checks pass.

Required fix

Add a Version 2 database migration that safely reconstructs event_scenarios
using the approved current schema and removes the obsolete legacy columns.

Do not work around the issue by writing placeholder values into obsolete
columns.

Do not modify the demand formulas or reinterpret old fields silently.

Migration compatibility policy

Use this explicit policy:

1. Databases with no existing Scenario rows:
   - Migrate automatically.

2. Existing Scenario rows that already contain complete and valid revised
   demand values:
   - Preserve those revised values.
   - Preserve the rest of the row.
   - Remove the obsolete legacy columns.

3. Existing Scenario rows that contain only legacy demand values, or whose
   revised demand values are missing or invalid:
   - Do not guess or reinterpret their meaning.
   - Abort the migration safely.
   - Roll back all migration work.
   - Preserve the original database unchanged.
   - Raise or report a clear compatibility error suitable for the established
     startup or recovery behavior.

The legacy expected_buyer_basis_points field represented a different business
meaning from expected_food_buyer_basis_points and must not be converted
automatically.
