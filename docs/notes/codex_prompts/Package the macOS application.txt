Installation and update model

Distribute the app through a drag-and-drop DMG.

The intended installation flow is:

1. Open the DMG.
2. Drag Food Truck Event Profit Calculator.app to Applications.
3. Eject the DMG.
4. Launch the application from Applications.

Support installation to either:

- /Applications
- The customer’s ~/Applications directory

Do not require administrator privileges from the application itself.

Updating the application consists of replacing the existing .app bundle with a
newer version.

Application replacement must not modify or remove customer data under
Application Support.

If the application is running during replacement:

- Document that it should be closed first.
- Do not implement a background updater.
- Do not modify active customer files from the DMG.

Reinstallation must reconnect to preserved customer data and open the
appropriate Welcome or Dashboard state.

Uninstallation consists of moving the .app to Trash.

Uninstallation must leave customer data intact, including:

- Business Defaults
- Events
- Scenarios
- Backups
- Recovery snapshots
- Logs

Do not add an automatic data-removal utility in this milestone.

Development and release build modes

Provide two explicit build modes.

Development mode:

- Build the complete standalone .app.
- Apply an appropriate ad-hoc signature where required.
- Create a development DMG when requested.
- Do not claim the output is Developer ID signed.
- Do not claim the output is notarized.
- Clearly label development artifacts and documentation accordingly.

Release mode:

- Require a valid Developer ID Application signing identity.
- Require the signing identity to be supplied through the build environment or
  keychain configuration.
- Sign all nested executable code correctly.
- Sign the outer application bundle last.
- Enable Hardened Runtime.
- Include a secure timestamp.
- Use only the minimum entitlements demonstrated to be required.
- Verify the application signature before producing the final DMG.
- Sign the DMG where appropriate.
- Submit the distribution artifact to Apple’s notary service using:
  xcrun notarytool
- Wait for the notarization result.
- Retrieve and preserve useful failure logs when notarization fails.
- Staple the successful notarization ticket.
- Verify the stapled ticket.
- Verify Gatekeeper acceptance.

Do not use altool.

Signing configuration

Read release signing configuration from secure build inputs.

Support an appropriate secure notarization-authentication method, such as an
existing notarytool keychain profile or approved App Store Connect API
credentials.

Do not:

- Commit certificates
- Commit private keys
- Commit Apple account passwords
- Commit app-specific passwords
- Commit notary credentials
- Print secrets in build logs
- Generate a fake Developer ID identity
- Use a self-signed identity while claiming a release build
- Proceed with release notarization when credentials are missing

When release signing is explicitly requested but configuration is unavailable:

- Fail clearly.
- Explain which category of configuration is missing.
- Preserve any valid unsigned development bundle separately.
- Do not rename the unsigned output as a release artifact.
